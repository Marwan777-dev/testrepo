## Backend Module Folder Structure & Data-Access Rule

Every backend file path below lands in the canonical structure (AMENDMENT-008 / AMENDMENT-009 / AMENDMENT-007 / DB-08), using the M-16 module `Nabadat.CustomerJourneyManagement` as the in-repo template (itself the M-10 `Nabadat.UserManagement` reference):

- **Naming (AMENDMENT-008):** projects/assemblies/namespaces/types use `Nabadat.<DomainName>` — **M-06 → `Nabadat.KpiManagement`**, **M-11 → `Nabadat.TenantAdministration`** (≠ the `Nabadat.TenantAdmin` host), **M-16 → `Nabadat.CustomerJourneyManagement`**. The `M{NN}` token MUST NOT appear in any project/assembly/namespace/type/test-project/fixture name (fixture is `KpiManagementApplicationFactory`). Hyphenated IDs `M-06`/`M-11`/`M-16` stay only as identifiers in prose.
- **Folders (AMENDMENT-009):** `Api/`, `Application/` (`Interfaces/` for context ports + one `<SubDomain>/` per concern), `Domain/` (`Entities/`, `ValueObjects/`, `Interfaces/` for ports + published interfaces), `Infrastructure/Persistence/` (+ `Configurations/`). A feature adds files into these existing folders — never a new top-level folder kind.
- **Data-access (AMENDMENT-007 / DB-08): NO repositories; ONE service per entity.** Each entity is fronted by a single **`<Aggregate>Service`** in `Application/<SubDomain>/` holding **both CRUD (EF Core over `ITenantDbContext`) and business logic** — there is NO separate `<Aggregate>DataService` (DB-08 and the M-10 `Nabadat.UserManagement` reference name it `<Aggregate>Service`, e.g. `TenantUserService`; the `*DataService` suffix is an M-16-local variation, not the standard). Its port `I<Aggregate>Service` lives in `Application/<SubDomain>/Interfaces/` (the unit-test mock seam); the `ITenantDbContext` context port in `Application/Interfaces/`; PUBLISHED cross-module interfaces in `Domain/Interfaces/`. EF maps the SQL-baseline schema via `IEntityTypeConfiguration<T>` per entity in `Infrastructure/Persistence/Configurations/`; `ITenantDbContext.ExecuteAsync` is the sole multi-write tx boundary (no unit-of-work type); SQL baseline owns the schema (no EF migrations); no raw ADO.NET / `FromSql*` / `ExecuteSql*` in feature code.
